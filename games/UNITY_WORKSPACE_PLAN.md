# Рабочее пространство Unity + Codex

Дата: 2026-09-09. Исходное архитектурное предложение; первый прототип
реализован в [Mosslight](mosslight/README.md).

Текущие решения: один Editor через Home Manager/Hub, запускаемый человеком;
Unity CLI MCP подключается к нему. CI проверяет только исходники без Unity.
Тяжёлые ассеты пока локальные и игнорируются Git; генератор и `.meta`
хранятся в репозитории. Более сложные этапы ниже остаются предложениями.

## Решение о репозитории

Оставить код, Unity-проект, инструменты и документацию в текущем monorepo.
Использовать существующие Nix, just, Gerrit, Zuul и рабочие навыки.
Unity открывает вложенный каталог проекта, а не корень monorepo.
Место хранения больших бинарных ассетов определить отдельно.

Отдельный репозиторий оправдан, если понадобятся собственные права доступа,
активная команда художников с блокировками файлов, Git LFS/другой VCS
или если размеры истории начнут мешать остальным проектам.
Отдельная рабочая копия того же monorepo также возможна: она изолирует
редактор от переключений ревизий во время инфраструктурных задач.

## Что подтверждено в существующем окружении

- Gentoo, niri/XWayland, Nix/Home Manager; Unity Editor 6000.6.0f1.
- Hub обёрнут в nixGL; FHS дополнен libtinfo и which.
- Старый фоновый Hub пережил switch: диагностика должна сравнивать
  запущенный процесс и установленный пакет, а не только версии на диске.
- Blender MCP прошёл initialize, tools/list и get_scene_info: 22 инструмента.
  Для blender-mcp 1.6.4 пришлось ограничить зависимость mcp<2.
  Проверено чтение сцены; экспорт, анимация и восстановление связи не проверены.
- Cothic имеет import/headless smoke и экспорт; MVP — тесты правил,
  запуск сборки, захват кадра, GIF и происхождение ассетов.
- Способы запуска Godot различаются. В MVP есть узкое исключение ошибки
  сертификата; это технический долг, а не доказательство провала подхода.
- В zuul.d/project.yaml Godot представлен gdlint; локальные smoke/экспорт
  не эквивалентны автоматически проверенной сборке в CI.
- .codex игнорируется Git; исправление Blender MCP сейчас машинное.
- scripts/sync_gym.sh экспортирует games: публичность нового проекта
  должна быть явной. Запуск sync не выполнялся.

## Выбор интеграции Unity

Прежний совет начать с Coplay необходимо пересмотреть: Unity официально
предлагает CLI для новых интеграций, включая MCP mode. В июльском анонсе
объявлена бесплатность CLI/MCP. Это обновляет майскую инструкцию,
которая требовала подписку Unity AI. Бесплатность интеграции не заменяет
проверку лицензирования самого Editor и сборочных машин.
[Официальный анонс](https://discussions.unity.com/t/announcing-the-unity-cli-a-new-way-to-connect-your-tools-and-agents/1731104).

CLI поддерживает структурированные ответы, управление установками и
локальную связь с Editor/Player через com.unity.pipeline. Pipeline описан
как experimental: маркетингового описания недостаточно для признания
нашей конфигурации надёжной.
[Обзор Unity CLI](https://unity.com/blog/meet-the-unity-cli).

Испытать официальный путь первым. CoplayDev/unity-mcp оставить кандидатом
при конкретном функциональном пробеле, а не запускать оба сервера сразу.
CLI/Editor scripts должны оставаться доступными для восстановления,
если MCP не поднялся или проект временно не компилируется.
[Coplay MCP](https://github.com/CoplayDev/unity-mcp).

## Команды и контракт автоматизации

Предлагаемый интерфейс — ещё не реализованные рецепты:

```text
just unity doctor
just unity editor
just unity status
just unity check
just unity test-edit
just unity test-play
just unity capture
just unity build
just unity smoke
just unity assets-export
```

Каждая команда явно выбирает проект и версию, возвращает статус и пути
артефактов, имеет тайм-аут. doctor проверяет запуск компилятора, GPU,
лицензию, версию живого процесса, MCP round-trip, свободное место и
готовность Editor. Логи очищаются от токенов перед выводом модели/CI.
Успешный tools/list не заменяет успешного вызова инструмента в Editor.

Одним проектом/Library управляет один Editor. Batch jobs используют
отдельную рабочую копию; параллельные изменения сцен запрещены по умолчанию.
Нельзя переключать ревизию под открытой сценой с несохранёнными изменениями.
Операции должны различать применено, сохранено, импортировано и проверено.
После timeout сначала читать состояние: повторное создание объекта может
дать дубликат. Изменения C# сохранять в исходниках; live eval не является
сохранённой реализацией фичи.

## Ассеты и структура

```text
games/<game>/
  AGENTS.md
  README.md
  justfile
  docs/                 # дизайн, арт, решения, проверка
  tools/                # doctor, export, тестовые сценарии
  art/                  # небольшие исходники и рецепты; политика крупных отдельно
  assets.lock.json      # при выборе внешнего хранилища
  unity/
    Assets/             # runtime-контент, C#, Editor scripts, Tests, .meta
    Packages/           # manifest.json и packages-lock.json
    ProjectSettings/    # включая ProjectVersion.txt
  artifacts/            # игнорируемые локальные результаты
```

В Git сохранять .meta вместе с ассетами, включить Force Text.
Library, Temp, Logs, Obj, UserSettings и сборки исключить до первого импорта.
Перемещать ассеты через Editor API либо вместе с .meta; проверять GUID
и отсутствующие ссылки. Не применять общий YAML-форматтер к Unity-файлам.
UnityYAMLMerge существует, но его подключение к jj нужно проверять отдельно.
[Unity Smart Merge](https://docs.unity3d.com/6000.0/Documentation/Manual/SmartMerge.html).

Git LFS нельзя считать готовым решением: документация jj перечисляет
Git LFS и .gitattributes как неподдерживаемые. Gerrit требует настройки
LFS endpoint/plugin. Отсутствие локальной конфигурации не доказывает
состояние сервера; полный upload/checkout/CI тест ещё не выполнен.
[Jujutsu Git compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/),
[Gerrit configuration](https://gerrit-review.googlesource.com/Documentation/config-gerrit.html).

Для первого среза — маленький набор ассетов в Git с явным бюджетом размера.
Для крупных исходников кандидат — существующее объектное хранилище:
неизменяемые объекты, hash/размер/версия в manifest, fetch по одной команде,
проверка checksum, резервное копирование и проверенное восстановление.
Альтернатива — отдельный репозиторий ассетов с Git LFS и обычным Git.
Не строить собственную систему хранения до появления реальной потребности.

Blender-источники держать вне Unity Assets; экспортировать согласованный
FBX-профиль и текстуры. На одном образце проверить метр, оси, pivot,
нормали, UV, rig и клип анимации. Материалы собирать под выбранный pipeline.
Для каждого внешнего ассета хранить источник и разрешённое использование.
Перед sync-gym явно определить, что публикуется, включая приобретённые ассеты.

## Skills и управление работой

Предлагаемые skills: unity-workspace (запуск/диагностика/выбор проекта),
unity-development (изменения/сохранение/проверка), game-assets
(Blender/export/import/provenance), game-validation (playtest/capture/perf).
Создавать их после испытания команд, с короткими инструкциями и ссылками
на исполняемые инструменты. Переиспользовать существующие Gerrit/Zuul skills.
[Skills в Codex](https://developers.openai.com/codex/skills).

Версии MCP, Python, зависимости и шаблон конфигурации хранить в репозитории.
Машинные абсолютные пути генерировать; секреты туда не включать.
Не подключать новый MCP для задачи, уже надёжно решаемой CLI.

Рабочий цикл: маленькая задача с видимым критерием → изменение → локальные
проверки → видео/скриншот и сборка → Gerrit → Zuul → ручная игровая оценка.
Каждая игровая задача описывает цель игрока и наблюдаемое поведение.
Человек оценивает удобство, интерес и визуальный результат; автоматические
тесты проверяют воспроизводимые свойства. DevOps не заменяет геймдизайн.

## CI и порядок внедрения

1. Создать маленький технический Unity-проект: сцена, камера, движение,
   физика, один импортированный ассет. Проверить официальный CLI/MCP.
2. Закрепить версии и launcher; перенести конфигурацию Blender MCP в
   воспроизводимую схему. Проверить reconnect и намеренную ошибку C#.
3. Ввести команды тестов, кадра, сборки и запуска Player. Покрыть важный
   игровой сценарий; не считать headless тест доказательством рендеринга.
4. Повторить цикл из чистого checkout. Закрепить экспорт Blender.
5. Добавить Zuul jobs: быстрые проверки; import/EditMode; PlayMode;
   Player build. Сохранять логи, XML, build report и сборку.
   [CLI Unity Test Framework](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html).
6. Отдельно проверить доступный способ лицензирования Unity на runner.
   GPU smoke выполнять на машине с графикой; CPU job не заменяет его.
   Кешировать Library по версии Editor, платформе и зависимостям, но
   периодически проверять сборку без кеша. Windows build проверять на
   Windows до обещаний о релизе, особенно при IL2CPP и native plugins.
7. После проверки workflow записать skills и начать первый игровой срез.

Критерий готовности: новая сессия агента по документации открывает проект,
меняет поведение, видит результат, получает тесты и собирает запускаемый
Player. Предлагаемая приёмка — три последовательных успешных цикла,
включая перезапуск Editor и чистый checkout. Замерять время и ручные
вмешательства; фиксировать ошибки процесса до расширения набора инструментов.

Неопределённости: жанр/арт-цель, платформа выпуска и целевая GPU,
модель распространения, бюджет ассетов, участие других людей,
лицензирование runner и поведение официального CLI на Gentoo/Nix.
Они не мешают первому техническому испытанию, но ограничивают финальный выбор.
